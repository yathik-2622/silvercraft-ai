## 4. LangGraph graphs

Unchanged this pass. **Ground truth:** the codebase contains exactly **one** hand-authored `StateGraph` outside the Orchestrator — the small `Send`-based task fan-out graph used internally by SolutionAgent's `.execute()`. SolutionAgent's `.plan()`, `.execute()`, and `_schedule_tasks()` are plain async Python functions and a for-loop over stages, not a graph. A third LangGraph object — `create_react_agent` (library-provided ReAct graph) — is instantiated fresh per task inside `ADM_run_task_worker`, not hand-authored here.

### Graph 1 — Orchestrator (`app/graphs/orchestrator_graph.py`, `ADM_build_orchestrator_graph`)

State: `ADM_OrchestratorState` (TypedDict) — `project_id: str | None`, `chat_id`, `message`, `file_refs`, `selected_skill_ids`, `orchestrator_model`, `derive_title`, `derived_title`, `tier`, `missing_info`, `response_text`, `matched_skill`, `matched_skills`, `modeling_style`, `citations`, `create_project_prompt`.

Nodes: `extract_intent`, `clarify`, `tier0_answer`, `route_tier3`.

Entry point: `extract_intent`.

Edges:
- `extract_intent` → conditional (`ADM_route_after_intent`) → `{clarify, tier0_answer, route_tier3}`
  - Routing logic: if `tier == "tier3"` and `missing_info` is non-empty → `"clarify"`; elif `tier == "tier0"` → `"tier0_answer"`; else → `"route_tier3"`.
- `clarify` → `END`; `tier0_answer` → `END`; `route_tier3` → `END`.

What each node does:
- `extract_intent`: one `ADM_chat_completion_json` call classifying tier0 vs tier3, `modeling_style`, a `missing_info` list, a suggested chat `title`, and a `suggested_domain`. Appends `"source"`/`"modeling_style"` to `missing_info` as needed; **inserts** `"project"` at index 0 if tier3 and `project_id` is falsy. Sets `create_project_prompt` whenever `"project"` is in `missing_info`.
- `clarify`: takes `missing_info[0]` only. `"project"` gets a fixed friendly `response_text` (frontend renders a structured card); otherwise a canned prompt string for `modeling_style`/`source`.
- `tier0_answer`: semantic search against `modeling_reference` (top_k=3), streams the answer token-by-token, then semantic search against `skills` (top_k=5) for `matched_skills`/`matched_skill`.
- `route_tier3`: sets a fixed "Got it — building your plan now" response; `plan_task` enqueue happens in `tasks.py`, not this node.

### Graph 2 — Task fan-out (`app/graphs/solution_agent_graph.py`, `ADM_get_fanout_graph`)

State: `ADM_FanoutState` — `dispatches: list[ADM_TaskDispatchState]`, `task_results: Annotated[list[dict], operator.add]`.

Nodes: `run_one_task_node` (one `ADM_execute_one_task` call per invocation).

Entry: **conditional entry point** — `ADM_fanout_router(state)` returns `[Send("run_one_task_node", {...}) for d in state["dispatches"]]`.

Edge: `run_one_task_node` → `END`.

Checkpointer: `MongoDBSaver`, pointed at the separate `adm2_agent_checkpoints` Mongo database (confirmed live: `checkpoints` + `checkpoint_writes` collections). `thread_id` = `"{contract_id}_stage_{stage}_batch_{batch_start}"`.

Caller (`ADM_run_tasks_via_send`): batches `planned_tasks` into groups of `max_workers`, invokes the graph once per batch (parallel within a batch, sequential across batches).

### Not a graph, but the thing that drives both of the above

`ADM_execute()` — plain Python `for stage in ADM_STAGE_ORDER` loop reading/writing the `run_state` collection directly, calling `ADM_run_stage()` → `ADM_run_tasks_via_send()` (Graph 2) → `ADM_hitl_manager_route()` (also plain Python). Any `pending` gate stops the whole `.execute()` call immediately.

### Graph 3 (library-provided) — TaskWorker's ReAct agent

`ADM_run_task_worker` calls `create_react_agent(model, declared_tools, prompt=system_prompt)` — one fresh instance per task, using only that skill's declared tools (now correctly excluding `db_metadata_introspector` for the 3 skills that used to list it — see §8). Streamed via `agent.astream_events(..., version="v2")` when `chat_id` is present, else a single blocking `.ainvoke()`.
