The Foundation Layer in `ADM_SILVER_LAYER` consists of **4 sequential stages**, each responsible for a specific phase of the data modeling lifecycle. Each stage is broken down into discrete steps that are executed via a combination of UI-driven workflows, backend agents (Azure Functions/LangGraph), and persistent session state. Below is a detailed breakdown of each stage, its steps, purpose, implementation approach, and the problem it solves.

---

## 📊 Overview
| Stage | Name | Steps | Primary Goal |
|-------|------|-------|--------------|
| 1 | Source Analysis | 7 | Profile, enrich, and understand raw source data |
| 2 | Conceptual Modeling | 2 | Derive high‑level business concepts and relationships |
| 3 | Logical Modeling | 10 | Convert conceptual model to a detailed logical schema (entities, attributes, keys, SCD, relationships) |
| 4 | Physical Modeling | 6 | Transform logical model into a deployable physical design (surrogate keys, naming, transformations, STTM, DDL/DML, artifacts) |

Total stages: **4**

### **4️⃣ Stage 4 – Physical Modeling**  
*Files:* `Stage4_PhysicalModeling.tsx`, `stage4/GenerateSurrogateKeysView.tsx`, `stage4/StandardizeNamesView.tsx`, `stage4/GenerateSttmView.tsx`, `stage4/GenerateDdlDmlView.tsx`  
*Steps (6):*  

| Step | What it Does | Why It Exists | How It’s Built |
|------|--------------|---------------|----------------|
| **1. Generate Surrogate Keys** | Determines whether surrogate keys are needed (mandatory for SCD Type 2 entities, optional otherwise), presents a draft plan, and lets the user review/confirm key names and data types (INT/BIGINT). | Surrogate keys provide a stable, immutable primary key for dimensional tables, insulating the model from business key changes and enabling accurate historical tracking. | **Assess‑then‑plan‑then‑confirm** HITL flow via `/api/v1/agents/surrogate-key/execute` (phase=`assess`/`plan`) and `/api/v1/agents/surrogate-key/confirm` agent. Uses `SurrogateKeyGeneratorAgent` (LangGraph) to evaluate SCD state, business keys, and relationships. Confirmed results are merged into the logical model as surrogate key attributes (`is_surrogate_key=true`, `surrogate_key_name`, `surrogate_key_type`) and persisted as the new active session state for downstream steps. |
| **2. These expressions are later embedded in the STTM and DDL generation steps. |
| **4. Generate STTM** | Runs the **sttm‑generator** agent to produce a Source‑to‑Target Mapping matrix that maps each logical attribute (after standardization and transformation) to a physical column, including data type, nullability, primary key flags, and SCD Type 2 markers. | Creates the authoritative blueprint for how the logical model will be physically instantiated in a database, bridging design and implementation. | Calls `/api/v1/agents/sttm-generator/execute` → outputs `SttmRow[]` (source/target entity/attribute, mapping expression, data type, `isPk`, `isScdType2`, etc.) → stored in `agentic_dm_stage4_sttm_v2`. |

No backend agent needed—artifacts are constructed from the confirmed session state (standardized model, STTM, DDL/DML). |

**How the stage is built overall:**  
- A linear six‑step workflow with modal‑driven review for each step (`GenerateSurrogateKeysView`, `StandardizeNamesView`, `GenerateSttmView`, `GenerateDdlDmlView`).  
- Surrogate key step uses a **three‑phase** HITL model (assess → plan → confirm) because it mutates the authoritative physical design; the other steps use a simpler **generate → confirm** pattern.  
- All agent executions are orchestrated via the API layer (`apis-azure`) which builds agent input from the current session state, triggers Azure Functions, and handles WebPubSub negotiation for real‑time progress.  
- The agent layer (`adm-foundation-layer-agents-azure`) contains the actual LangGraph‑based agents (e.g., `SurrogateKeyGeneratorAgent`) that perform deterministic rule‑based processing.  
- Confirmed outputs from each step are written back to the metastore (`dfl_adm_session`) as the new active session version, ensuring that downstream steps always consume the latest verified design.  
- The stage makes heavy use of `usePersistentState` hooks to preserve intermediate state (e.g., `surrogateKeyPlans`, `surrogateKeyAssessment`, `isStandardizeNamesConfirmed`, `transformationRules`) across navigations and refreshes.

---

## 🧩 Summary
- The Foundation Layer is a **four‑stage, twenty‑five‑step** pipeline that takes raw source data through profiling, conceptualization, logical detailing, and physical design generation.  
- Each stage is **modular**, with clearly defined steps that are implemented as combinations of **UI workflows**, **backend agents (Azure Functions/LangGraph)**, and **persistent session state**.  
- The design emphasizes **Human‑In‑The‑Loop (HITL)** validation at critical junctures (especially where mutations to the authoritative model occur, such as surrogate key assignment and naming standardization) to ensure correctness and traceability.  
- Agents are **decoupled and reusable**; each step invokes a specific agent that performs a narrowly scoped, deterministic function (e.g., profile‑data, map‑attributes, standardname, sttm‑generator).  
- State flows strictly forward: the output of one stage becomes the input of the next, with the ability to revisit prior steps for correction before final confirmation.  
- The ultimate goal is to produce a **verified, deployable physical model** (DDL/DML, STTM, artifacts) that accurately reflects the source data’s semantics while adhering to best practices for dimensional modeling, naming conventions, and data quality.

This layered, step‑wise approach ensures that complex data modeling tasks are broken into manageable, reviewable increments, reducing errors and increasing collaboration between technical and business stakeholders. No code was modified or altered during this analysis.

Generate STTM** | Creates source-to-target mapping document showing lineage from source to target | Documents how logical attributes map to physical columns including transformations, data types, and SCD Type 2 markers; essential for ETL development and data lineage tracking | Modal (`GenerateSttmView`) triggers `/product/v1/agents/sttm-generator/execute` agent → returns `SttmRow[]` with mapping details → user can edit mappings and select target entity → confirmed STTM enables progression to DDL/DML generation |
| **3. Generate DDL and DMLs** | Creates physical schema and loading scripts (`CREATE TABLE`, `INSERT` statements) | Transforms the approved physical design into executable database scripts for deployment to target systems (e.g., Databricks, Snowflake, SQL Server) | Modal (`GenerateDdlDmlView`) triggers `/product/v1/agents/sqlgenerator/execute` agent → returns DDL/DML scripts per entity → user can select entity to view scripts → confirmed scripts enable progression to KPI Logic finalization |
| **4. Finalise KPIs** | Generates and validates KPI SQL logic for implementation | Produces executable SQL logic for each KPI that can be deployed to the target environment; ensures KPIs are correctly calculated from source data | Modal (`GenerateKpiLogicView`) triggers `/product/v1/agents/kpigenerator/execute` agent → returns KPI SQL logic catalog → user reviews and confirms logic → confirmed KPIs enable progression to Artifacts Download |
| **5. Download Artifacts** | Exports all generated models and scripts for deployment | Provides deliverable artifacts to DBAs, developers, or CI/CD pipelines for actual database creation and KPI implementation | Modal (`DownloadArtifactsView`) shows list of available artifacts (SQL scripts, JSON definitions, reports) → user confirms download readiness → final completion of Product Layer workflow |

**How the stage is built overall:**  
- Five-step sequential workflow with special dependency rules: <br> • DDL/DML step can be accessed after Standardize Names (skipping STTM if needed) <br> • KPI Logic step requires DDL/DML completion <br> • Download step is final and requires all prior steps |  
- Modal-driven interaction for each step with dedicated views: <br> • `StandardizeNamesView` <br> • `GenerateSttmView` <br> • `GenerateDdlDmlView` <br> • `GenerateKpiLogicView` <br> • `DownloadArtifactsView` |  
- Agent execution follows consistent pattern: <br> 1. Trigger agent via `/product/v1/agents/<agent-name>/execute` <br> 2. Connect to WebPubSub for real-time progress logging <br> 3. Fetch results via `/product/v1/agents/get_agent_execution_result` <br> 4. Transform and persist results to session state |  
- State persistence via `usePersistentState` hooks for: <br> • Completed steps (`product_dm_stage4_completedSteps`) <br> • Active step (`product_dm_stage4_activeStep`) <br> • DDL scripts (`product_dm_stage4_ddlScripts`) <br> • DML scripts (`product_dm_stage4_dmlScripts`) <br> • STTM (`product_dm_stage4_sttm`) <br> • Selected entities for DDL/STTM viewing <br> • Standardized names result (`product_dm_stage4_standardizedNamesResult`) <br> • KPI catalog (`product_dm_stage4_kpiCatalog`) <br> • Stage logs (`product_dm_stage4_stageLogs`) <br> • Session ownership tracking (`product_dm_stage4_sessionOwner`) |  
- Sophisticated step dependency logic with conditional access rules (e.g., DDL/DML accessible after Standardize Names regardless of STTM completion) |  
- Real-time logging via WebPubSub with stage-specific log accumulation in `stageLogs` state |  
- Special handling for session ownership to prevent conflicts when multiple users work on same session |  
- Cleanup functions (`clearStepDataFrom`, `resetProgress`) to manage state when revisiting steps or restarting workflow |

## 🔬 Special Features: Surrogate Key Agent in Product Layer

Similar to the Foundation Layer in Silver, the Product Layer includes a **SurrogateKeyAgent** (`adm-product-layer-agents-azure/agents/SurrogateKeyAgent/`) that determines primary key strategies for KPI/aggregate tables. However, this agent serves a different purpose:

### **Product Layer Surrogate Key Agent**
- **Purpose**: Determines whether to use natural-composite keys or surrogate keys for gold-layer KPI/aggregate tables
- **Input**: KPI mappings and source table metadata from previous stages
- **Output**: `SurrogateKeyDecisions` containing:
  - `table_name`: Gold table name
  - `table_role`: Fact, dimension, or aggregate
  - `primary_key_strategy`: "natural-composite" or "surrogate_key"
  - `primary_key`: Selected business key columns (if natural-composite)
  - `surrogate_key`: Selected surrogate key name (if surrogate key)
  - `final_primary_key`: Final selected primary key
  - `justification`: Business reasoning for the choice
- **Decision Logic**:
  - Uses rule-based heuristics to classify table roles (fact/dimension/aggregate)
  - Identifies key candidates from source table metadata
  - Evaluates time requirement for keys (essential for SCD Type 2 support)
  - Leverages LLM (GPT-4o-mini) with structured prompts for complex decisions
  - Includes robust fallback to surrogate key strategy when LLM output is invalid
  - Supports user override for manual key selection
  - Generates deterministic surrogate key names (`<table_name>_sk`)
- **Key Differences from Foundation Layer Surrogate Key Agent**:
  - Focuses on KPI/aggregate tables rather than dimensional modeling entities
  - Determines key strategy rather than generating surrogate key columns
  - Outputs decisions rather than modifying the logical model directly
  - Used during KPI finalization stage rather than physical modeling stage

## 🧩 Summary
The Product Layer in `ADM_GOLD_LAYER` is a sophisticated KPI/data product modeling workflow consisting of **4 stages with 18 total steps** that takes users from source configuration through KPI discovery, finalization, and physical implementation. 

Key architectural characteristics:
1. **Modular Stage Design**: Each stage is a self-contained workflow with clear entry/exit points
2. **Human-In-The-Loop (HITL) Validation**: Critical decisions require user confirmation before progression
3. **State Persistence**: Comprehensive use of `usePersistentState` hooks maintains workflow state across navigations and refreshes
4. **Agent Orchestration**: Backend agents (Azure Functions) handle complex AI/ML operations with real-time progress tracking
5. **Conditional Workflows**: Different paths based on input method (chat vs file upload) optimize user experience
6. **Dependency Management**: Sophisticated step activation logic ensures users complete prerequisites before advancing
7. **Extensibility**: Clear separation of concerns makes it straightforward to add new steps or modify existing ones

The Product Layer complements the Foundation Layer by focusing specifically on KPI/product definition and implementation, while the Foundation Layer handles general data modeling. Together, they form a complete data modeling solution that supports both enterprise data warehousing (Foundation Layer) and specialized KPI/product development (Product Layer).

Total stages across both layers: **8** (4 Foundation + 4 Product)  
Total steps across both layers: **43** (25 Foundation + 18 Product)
